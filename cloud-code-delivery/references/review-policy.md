## 1. 目标

代码任务在提交和生成结果包前必须完成一次独立或主线程 diff 审查。审查用于发现
正确性、回归、测试和结构问题，不替代任务单验收、构建、测试或运行验证。

## 2. 审查范围

审查输入只包含：

- 任务单中的目标、非目标、允许路径和验收条件；
- `base_commit` 到待提交工作树的实际 diff，或审查时已形成的 `base_commit..HEAD`；
- 变更文件及受影响调用方、共享辅助代码和测试；
- 已执行的构建、测试和静态检查结果；
- 项目上下文文档与源码之间已确认的差异。

reviewer 不读取完整会话历史，不修改文件，不创建提交，也不继续委托其他 reviewer。

重点检查：

- 行为是否符合任务单，是否存在遗漏的验收项；
- 是否引入回归、边界条件错误、资源泄漏或错误处理缺口；
- 测试是否覆盖根因和主要风险，验证证据是否真实；
- 是否残留旧入口、旧参数、重复实现或无边界分支；
- 主入口是否保持薄层，新行为是否进入职责单一的模块；
- 是否存在无关重构、格式化噪声或文件膨胀。

## 3. 执行方式

优先使用只读 subagent，条件允许时把第 2 节输入整理成独立 review prompt。任务风险
较低、云电脑没有 subagent，或启动独立 reviewer 不具成本效益时，在主线程完成同等
范围的审查。

无论采用哪种方式，都必须：

1. 先完成与修改对应的构建、测试或静态检查；
2. 阅读完整 diff 和受影响上下文；
3. 按严重程度列出问题；
4. 修复有效问题后重新验证；
5. 没有发现问题时明确说明残余风险或测试缺口。

## 4. review.md 合同

有代码修改时，在 `output_path` 生成 `review.md`：

```markdown
# Code Review: <task_id>

- mode: subagent | main-thread
- base_commit:
- reviewed_tree: working-tree | base_commit..HEAD
- result_commit: pending | <sha>
- reviewed_files:

## Findings

## Resolution

## Residual Risk
```

没有发现时在 `Findings` 写 `none`。未修复的问题必须写明影响和未验证项；不能把未解决
问题隐藏在总结中。提交完成后把 `result_commit` 从 `pending` 更新为实际提交 SHA。
`review.md` 只能记录实际完成的审查，不能伪造 reviewer 或结论。

## 5. 停止条件

出现以下情况时不得提交或标记 `DONE`：

- 有代码修改但没有完成 diff 审查；
- reviewer 输入与实际提交范围不一致；
- 仍有未处理的高严重度发现；
- 审查依赖的验证结果缺失或无法与实际源码对应；
- 只能通过修改任务范围或引入无关改动才能解决发现。

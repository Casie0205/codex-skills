# 口播稿：基于 AnalysisHub 与 AnalysisHub-CLI 的 GNSS 原始数据分析 Skill

## 第 1 页：今天想解决什么问题

大家好，今天我分享的主题，是基于 AnalysisHub 和 AnalysisHub-CLI，怎么把现有的 GNSS 原始数据分析能力做成一个可复用的 Skill。

我先讲问题。其实我们现在不是没有工具，AnalysisHub 本身已经很强，AnalysisHub-cli 也已经具备很多命令行能力。问题不在于算法不够，而在于使用门槛偏高。GUI 很适合熟手做探索，但不适合标准化复用；CLI 很适合批处理，但对很多同事来说，命令并不好记，文件之间怎么搭配也不够直观。

另外一个现实问题是，结果文件很多。比如 QC.html、DF.html、TF.html、DataList.log、还有 .DF、.TF 这些数据文件，经常在一个目录里同时存在。熟手一看就知道怎么走，非熟手就很容易迷路。最后就会出现一个情况，就是同样一套能力，真正能高效用起来的人其实不多。

所以今天想做的事情，不是重新发明工具，而是把“会用工具的经验”沉淀成一个 Skill。

## 第 2 页：核心思路

这页我想把边界先说清楚。我们不是重做算法，不是替代 AnalysisHub，也不是让大模型自己去算 GNSS。GNSS 的实际计算、质检、绘图、报表生成，仍然是 AnalysisHub 和 AnalysisHub-cli 在做。

Skill 做的事情，是在这些能力之上加一层智能入口。用户只需要描述自己想做什么，Skill 负责识别意图、识别文件、决定走 GUI 还是 CLI、组织命令，然后把结果再解释成人能快速理解的话。

所以我觉得这件事最准确的一句话是：算法没有变，变的是入口。

## 第 3 页：现有工具能力基础

这里列一下我们现在已有的基础。当前 AnalysisHub-cli 已经支持单站质检，也就是 obscheck；支持历元间双差和三差；支持零基线和短基线残差分析；支持健康报表和 RTK 诊断报表；支持绘图；还支持 QC HTML 的批量合并。

除此之外，GUI 还有一个很关键的优势，就是体检报表能跟随当前 QC、DF、TF 模式切换。这个点非常重要，因为它决定了 Skill 不能只会拼 CLI 命令，还必须知道 GUI 和 CLI 在能力边界上的差异。

也就是说，我们做 Skill 不是在纸上设计，而是完全基于现在已经存在的实现。

## 第 4 页：为什么要做 Skill，而不是只讲 CLI

有人可能会问，那是不是把 CLI 文档写全一点就够了。我的判断是不够。因为真正的问题不是“有没有命令说明”，而是用户在面对一个目录时，根本不知道该走哪条流程。

比如一个目录里同时有 QC、DF、TF 结果，还有 DataList.log，还有差分数据文件。这个时候问题已经不是某个参数怎么写，而是我要先识别这是什么场景，我要知道哪个流程能走 CLI，哪个流程必须走 GUI，我要知道结果出来之后先看什么。

所以 Skill 的价值，不是在于代替文档，而是在于把这些经验显式化，形成一个可执行的工作流。

## 第 5 页：Skill 设计结构

现在这个 Skill 我拆成了几层。第一层是 SKILL.md，里面定义触发条件、路由规则和标准输出格式。第二层是文件模式识别规则，比如哪些文件代表 QC，哪些文件代表 DF 或 TF，哪些组合可以生成健康报表。第三层是 CLI 能力清单，明确写清楚当前命令面到底支持什么。第四层是分析 playbook，也就是如果工具已经给了结果，AI 应该怎么组织解释。

除此之外，我还给这个 Skill 补了演示提词、Demo 脚本、交互式反问流程，以及 GUI 拉起的 handoff 规则。因为这次不仅是做一个 Skill，还要把它变成一个能讲、能演示、能落地的材料。

## 第 6 页：我希望 Skill 最终达到的体验

这一页我想讲目标体验，而不是当前命令列表。理想状态下，用户不需要先知道 obscheck、diff-epoch、triple-epoch 这些词。用户只需要说一句，先分析下这个数据。

这个时候 Skill 应该先看路径里有什么文件，然后只问真正缺失的问题。比如这个数据希望按什么解码类型处理，希望先看 QC、DF 还是 TF，是只想先快速判断一下，还是要完整体检报表。

等处理完以后，Skill 默认应该给出三层东西。第一层是报表路径，第二层是 AI 总结，第三层是后续动作，也就是如果你还想看异常图，我可以继续把 AnalysisHub GUI 拉起来。

我觉得这一层非常关键，因为这才像一个分析助手，而不只是一个命令行包装器。

## 第 7 页：Skill 的工作流程

这个 Skill 的工作流程其实很清晰，一共五步。

第一步，先识别目录中的 GNSS 分析产物。第二步，判断用户是要做 QC、做 DF/TF、做体检报表、做绘图，还是做批量汇总。第三步，决定走 GUI 还是 CLI。第四步，真正调用 AnalysisHub 或 AnalysisHub-cli。第五步，把结果整理成结论、异常项、重点时间窗，以及建议下一步看哪里。

这里我想强调一下，关键不是把所有事情都强行塞进 CLI，而是要尊重当前工具的真实实现。Skill 最重要的能力之一，不是“会调用”，而是“不会乱调用”。

## 第 8 页：GUI 与 CLI 的边界

所以这一页专门讲边界。当前我建议的边界是这样的：如果是批处理、单站质检、无界面出图、QC 健康报表、或者批量合并，这些都更适合走 CLI。因为它稳定、可复现、适合自动化。

但如果任务依赖当前 GUI 页面状态，比如用户已经切到了 DF 模式或者 TF 模式，再点体检报表，这种模式联动的能力当前就是 GUI 更合适。尤其是 DF、TF 下的精度异常卫星频点表，这种能力当前要尊重 GUI 的实际工作流。

我觉得这点特别适合拿来讲 AI 技巧。因为真正好的 Skill，不是“什么都说自己能做”，而是能准确知道自己该把任务交给谁。

## 第 9 页：一个真实样例目录

这里我用一个真实样例目录来说明。这个目录里同时存在 QC、DF、TF 的 HTML，存在 DataList.log，也存在 .DF 和 .TF 数据文件。

对于人来说，这已经是一个典型的“熟手知道怎么走，生手容易懵”的场景。但 Skill 看这个目录的时候，会把它拆成几个明确的候选路径。比如 QC 的健康报表可以走 CLI，DF 和 TF 的模式跟随健康报表应该走 GUI。

也就是说，Skill 的第一步不是立刻执行，而是先把“可走路径”讲清楚。这个动作本身就已经节省很多沟通成本了。

## 第 10 页：Demo 1，识别目录产物

第一个 Demo 我建议直接让用户说一句话：先识别这个目录里有哪些 GNSS 分析产物，告诉我能走哪些 AnalysisHub 或 AnalysisHub-cli 流程。

这里展示的重点，不是命令本身，而是 Skill 的认路能力。它会告诉你，这个目录里有哪些 QC、哪些 DF、哪些 TF、有没有 DataList.log、有没有差分数据文件，然后告诉你有哪些流程现在可以合法地走。

这个 Demo 的意义在于，让大家一上来就看到，AI 不是“接到问题就生成一串命令”，而是先理解上下文。

## 第 11 页：Demo 2，生成 QC 体检报表

第二个 Demo 就进入执行。问题可以是：基于这个 _QC.html 和 DataList.log，生成数据体检报表，并总结最主要的异常项。

这个时候 Skill 会走 CLI 的 report health 路径，生成 health.html、health_report.html、总览图以及一系列异常 CSV。然后 AI 再把这些结果压缩成一个人能直接读懂的摘要，比如总体结论是什么，主要异常集中在哪里，重点时间窗是什么，建议下一步先看哪一张表或者哪一张图。

这个 Demo 展示的是流程编排能力。也就是工具能力本来已经在那，但 Skill 把它组织成了一个更像“分析助手”的体验。

## 第 12 页：Demo 3，说明 DF / TF 模式差异

第三个 Demo 我建议不要只是跑命令，而是专门讲能力边界。比如提一个问题：如果我切到 DF 模式再点体检报表，现在工具会走什么逻辑，和 CLI 的 report health 有什么区别。

这个问题很适合展示 Skill 的边界意识。它应该告诉你，当前 GUI 是跟随当前模式走的，DF 和 TF 模式下还能联动生成伪距和载波精度异常卫星频点表；而 CLI 当前暴露的是 QC 风格健康报表入口，不能把 GUI 的模式联动能力说成 CLI 已经完全具备。

这个 Demo 的价值在于，它让大家看到，一个好的 Skill 不是“吹能力”，而是能把真实能力边界说明白。

## 第 13 页：为什么这件事有业务价值

从研发角度看，这件事的价值是流程更标准、经验更容易沉淀。从测试和支持角度看，价值是少记命令、少猜文件关系、更快拿到可转述的结论。从组织角度看，最大的价值是把原来掌握在少数熟手身上的经验，变成一个可安装、可更新、可复用的 Skill。

我觉得这也是这次分享最适合对外传达的一点。我们不是为了 AI 而 AI，而是在解决工具能力复用的问题。

## 第 14 页：如何随发版更新

这一页讲落地。这个 Skill 现在已经不是散文件了，而是做成了一个可发布包。源 Skill 独立维护，Release 目录下面放 codex-skills 包，用户侧用安装脚本来安装和升级，Skill 自带 manifest 做版本识别。

这意味着以后它可以随着 AnalysisHub 发版一起更新。流程也很简单，改源 Skill，发布到 Release，用户执行安装脚本。这样它不再是一次性的分享材料，而是可以变成真正跟产品一起演进的能力。

## 第 15 页：今天的结论

最后我想把结论收回来。我们今天做的不是一个新的 GNSS 算法，而是一层 GNSS 分析能力的 AI 入口。这层入口完全建立在现有的 AnalysisHub 和 AnalysisHub-cli 之上。它的价值不在于替代工具，而在于让工具更容易被调用、更容易被解释、更容易被复用。

如果用一句话做结尾，我会说：把会用 AnalysisHub 的个人经验，沉淀成所有人都能调用的 Skill。

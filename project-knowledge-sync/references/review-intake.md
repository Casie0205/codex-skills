## 1. 输入类型

| 输入 | 可作为证据的内容 | 不能直接推出的内容 |
| --- | --- | --- |
| 云电脑文本回复 | 路径、符号、行号、代码片段、运行结果 | 未显示的函数体、配置和分支 |
| 源码截图 | 可见代码、结构字段、调用关系 | 截图外的上下文、完整宏展开 |
| 运行日志 | 命令、退出码、时序和错误路径 | 未打印的变量和隐藏状态 |
| 用户摘要 | 用户明确确认的结论 | 用户未说明的实现细节 |
| 设计说明 | 设计意图和约束 | 当前源码一定已经实现该设计 |

## 2. 结论拆分

把输入拆成单条声明。每条声明包含：

```text
review_id:
branch:
commit:
claim_id:
current_statement:
proposed_statement:
code_path:
symbol:
line_or_anchor:
snippet:
observation:
status:
affected_documents:
remaining_question:
```

一条声明出现多个函数、多个分支或多个独立行为时继续拆分，直到每条结论可以单独验证。

## 3. 证据判定

- 路径、符号、可核对定位（行号、稳定锚点或最小片段）和观察一致时，才可标为
  `confirmed-cloud`。只有路径、符号和概括观察时保持 `open`。
- 只有本地截图或旧文档明确显示时，标为 `confirmed-local`。
- 观察到与旧文档相反且证据明确时，审查结论标为 `corrected`；合并后的新结论按证据
  等级标记为 `confirmed-cloud` 或 `confirmed-local`。
- 只有调用关系或命名依据时，标为 `inferred`。
- 缺少源码路径、符号、可核对观察、配置或运行结果时，标为 `open`。
- 新结论完全替代旧结论时，旧条目标为 `superseded`。

证据不足时宁可不合并，也不使用“应当”“可能”“看起来”作为结论。

## 4. 合并矩阵

| 结论类型 | 首选位置 |
| --- | --- |
| 分层、模块边界、端到端数据流 | 项目总览或 Framework |
| 单入口、单阶段控制流 | 对应 Flow 文档 |
| 结构体、字段、生命周期、不变量 | 数据结构文档 |
| 构建、配置、运行和日志 | 构建与运行文档 |
| 尚未回答的问题 | 知识缺口文档 |
| 原始云电脑回复 | 项目 `reviews` 目录 |

修改前先搜索现有同主题章节。已有章节能回答同一问题时，合并到该章节，不新建重复文档。

## 5. 审查记录更新

原始记录保留：

- review_id、日期、项目、仓库、分支和提交；
- 目标本地文档；
- 云电脑原始 `DOC-REVIEW` 块；
- 本地合并状态：`pending`、`partial`、`merged` 或 `rejected`；
- 已合并文档和未解决项。

综合文档只写合并后的结论，并从更新记录或证据表链接原始审查。

## 6. 冲突处理

发现冲突时：

1. 保留旧表述和旧证据。
2. 增加新证据和适用范围。
3. 判断是版本差异、分支差异、同名符号还是旧文档错误。
4. 无法区分时保留 `open`，不要强行选一个。
5. 确认替代关系后，把旧条目标记 `superseded` 并链接新结论。
